# AI Advisor 채팅 API 실측 결과

테스트 일자: 2026-09-09, Asia/Seoul(KST) 09시대  
대상: `POST http://192.168.0.157:8793/api/chat`  
판정: **내부망 통신·표 조회·세션 기능은 확인했다. AI Advisor 적용 전 CORS, 업무 오류 구분, 공백 입력 검증, 후속 질문 안정성을 보완해야 한다.**

현재 개발 PC에서 Node.js HTTP 클라이언트로 직접 요청했다. 인증 헤더 없이 연결되었고, 회사 데이터의 조회와 테스트용 대화 세션 생성만 수행했다. 부하 테스트는 하지 않았다. UI와 실제 연동 코드는 수정하지 않았다.

총 **25회** 요청했다: 채팅 POST 20회(200 11회·422 9회), OPTIONS 2회(모두 405), 서버 상태·메타데이터·OpenAPI GET 3회(모두 200). HTTP 200 채팅 11건의 응답 시간은 **8.824~18.843초, 평균 14.169초, 중앙값 13.484초**였다. 이 시간에는 업무 오류와 공백 입력 응답도 포함된다.

통신 성공을 의미하는 HTTP 200과 업무 답변 성공을 구분해야 한다. 이번 테스트에서는 SQL 생성·검증 실패도 `answer` 문자열로 내려왔다. 반대로 정상 단일 값 답변이나 빈 결과에도 `table: null`이므로, 표 유무만으로 성공·실패를 판단할 수 없다.

## 2. 요청·응답 계약 확인

사용자가 제공한 이미지와 실제 서버의 `GET /openapi.json`을 비교했다.

| 필드 | 서버 OpenAPI 계약 | 실측·연동 메모 |
| --- | --- | --- |
| 요청 `query` | 필수 문자열, 1~2,000자 | 2,001자 거절 확인. 공백 문자열은 통과하므로 별도 `trim()` 검증 필요 |
| 요청 `session_id` | 선택, 문자열 또는 null, 최대 128자 | 생략 시 UUID 생성, 지정 UUID 재사용 확인. UUID가 아닌 짧은 문자열도 그대로 허용 |
| 요청 `max_results` | 선택 정수, 1~10, 기본값 5 | 이미지에는 없는 필드. 0은 거절. 1로 지정해도 상위 3개 질의의 표는 3행이어서 표 행 수 제한으로 사용할 수 없음 |
| 응답 `answer` | 문자열 | 한국어 JSON 수신 정상. 일반 안내, 업무 답변, 업무 오류가 모두 이 필드에 담김 |
| 응답 `session_id` | 문자열 또는 null, OpenAPI상 선택 | 측정한 HTTP 200 응답에서 모두 값 반환 |
| 응답 `table` | 객체 또는 null | 단일 값은 본문만 반환될 수 있음 |
| `table.columns` | `string[]` | 요청에 따라 열 구성·순서가 달라짐 |
| `table.rows` | `string[][]` | 관측된 표는 셀이 문자열이고, 각 행의 셀 수가 열 수와 일치 |
| `table.truncated` | boolean, 기본값 false | 195건 안내/100행 반환 사례에서 true 확인. 이 한 건으로 모든 질의의 상한이 100행이라고 단정할 수는 없음 |
| `table.summary` | 문자열 값을 갖는 객체 | 관측된 표 6개에서는 모두 빈 객체. 내용이 있는 summary는 미검증 |
| 추가 응답 필드 | `sources`, `model_used`, `intent`, `sql` | 이미지 외 필드. 화면에 SQL이나 원본 출처를 자동 노출할 필요는 없음 |

정상 응답은 `Content-Type: application/json`이었다. 응답 헤더와 최초 본문이 생성 완료 시점에 거의 함께 도착했으며, SSE/토큰 스트리밍은 관측되지 않았다. 네트워크 청크 분할 여부와 모델 스트리밍은 구분했다.

수신한 표 6개·113행을 검사해 모든 행의 열 수 일치와 셀 문자열 타입을 확인했다. 수신 JSON에서 한글 디코딩 대체 문자도 발견되지 않았다. 195건이라는 전체 건수는 서버 답변 기준이며 원본 DB와 독립적으로 대조하지 않았다.

| 입력 오류 사례 | HTTP | 소요 시간 | 오류 유형 |
| --- | --- | --- | --- |
| `query` 누락 | 422 | 5ms | `missing` |
| 빈 문자열 | 422 | 3ms | `string_too_short` |
| null | 422 | 3ms | `string_type` |
| 숫자 타입 | 422 | 3ms | `string_type` |
| `query` 2,001자 | 422 | 4ms | `string_too_long` |
| `session_id` 129자 | 422 | 3ms | `string_too_long` |
| 깨진 JSON | 422 | 3ms | `json_invalid` |
| `Content-Type: text/plain`으로 JSON 문자열 전송 | 422 | 6ms | `model_attributes_type` |
| `max_results: 0` | 422 | 3ms | `greater_than_equal` |

422 오류 본문은 문자열이 아닌 `detail` 배열이었다. UI에는 필드별 오류를 한국어로 변환하거나 공통 입력 오류로 표시해야 한다.

### 후속 질문 재현 순서

1. 세션 없이 `2026년 8월 24일 자재 소요량을 소요량이 큰 순서로 상위 3개만 표로 보여주세요.`를 전송하고 응답 `session_id`를 저장한다.
2. 같은 세션에서 `방금 조회한 날짜를 유지하고 상위 1개만 보여주세요.`를 전송하면 이번 측정에서는 SQL 검증 실패가 발생했다.
3. 같은 세션에서 `방금 조회한 날짜 기준으로 실제·실적 수량은 제외하고 계획 소요량이 가장 큰 자재 1개만 보여주세요.`로 명확히 하면 정상 답변이 돌아왔고, 반환 SQL의 날짜는 8월 24일이었다.
4. 별도 UUID로 8월 25일을 조회한 B 세션에서도 3번 질문을 보냈을 때 8월 25일이 유지됐다.

따라서 세션별 날짜 문맥 유지 기능은 확인했지만, 모든 후속 질문이 안정적으로 처리된다는 의미는 아니다. 세션 만료·서버 재시작 이후 보존·다중 사용자 접근 제어는 이번 테스트 범위에 포함하지 않았다.

## 4. CORS와 배포 경로

`Origin: http://localhost:3000`, 요청 메서드 POST, 요청 헤더 content-type 조건으로 OPTIONS 사전 요청을 두 차례 보냈다. 모두 **405 Method Not Allowed**였고 `Access-Control-Allow-Origin` 등 CORS 허용 헤더가 없었다. 같은 Origin을 넣은 정상 POST 응답에도 허용 헤더가 없었다.

이번 검사는 사전 요청을 HTTP 클라이언트로 재현한 것이며 브라우저 화면 연동 시험은 아니다. 현재 관측 결과로는 다른 출처의 화면이 `application/json`으로 직접 POST하는 경로를 사용할 수 없다. 프로젝트의 Next.js 서버 라우트가 내부 API를 호출하고, 브라우저는 프로젝트와 같은 출처의 라우트를 호출하도록 구성하는 방안을 권장한다. Next.js 배포 서버도 `192.168.0.157:8793`에 접근할 수 있어야 한다. 현재 개발 PC의 연결 성공만으로 배포 서버의 접근 가능성을 보장하지 않는다.

브라우저 직접 호출을 선택한다면 API 서버에 실제 프론트엔드 출처의 OPTIONS/POST CORS 설정을 추가하고 해당 출처에서 다시 확인해야 한다.

## 5. 데이터 상태와 답변 품질

`GET /api/health`는 HTTP 200, `status: ok`, `model_loaded: true`, `data_error: null`, `model_error: null`이었다. 응답 시간은 245ms였다. `GET /api/data-meta`는 HTTP 200, 71ms였다.

| 메타데이터 | 값 |
| --- | --- |
| 재고 스냅샷 날짜 | 2026-08-01 |
| 데이터 기준일 | 2026-08-21 |
| 예측 종료일 | 2026-08-31 |
| 제공 뷰 수 | 17개 |
| `invalid_productivity_row` | 6건 |
| `missing_inventory_snapshot` | 4건 |

날짜와 이슈 건수는 서버가 보고한 값을 옮긴 것이다. 원본 DB나 MES와 대조하지 않았으므로 집계값의 업무 정확성·누락 여부를 검증한 결과는 아니다. Advisor에서 데이터 기준일과 품질 이슈를 전달하는 것이 필요하다.

추가로 단일 값 답변 한 건에서 긴 부동소수점 꼬리가 본문에 그대로 표시됐다. 수량의 표시 자릿수와 단위를 서버 답변 생성 단계에서 정리할 필요가 있다. 표의 숫자 표시도 숫자 열에 한해 `toLocaleString('ko-KR')` 등 프로젝트 규칙을 적용하고, 품목코드 문자열은 숫자로 변환하지 않아야 한다.

적용 순서는 다음과 같다.

1. 서버 API에서 공백 입력 거절, 기계적으로 구분 가능한 성공·빈 결과·업무 오류 필드를 정하고 후속 질문 실패를 보완한다. 단순 일반 질문은 지원 범위를 안내하도록 처리한다.
2. Next.js에 서버 전용 API 주소 설정과 연결 라우트를 마련한다. 기존 Ollama 라우트의 사용처를 고려해 새 계약을 분리하거나 명시적으로 변환한다.
3. 공통 Advisor에 세션 관리, 응답 전체가 올 때까지의 로딩, 제한 시간·취소, 사용자 재시도, 빈 결과 안내, 표 표시를 연결한다. 세션 기반 요청의 자동 재시도는 중복 대화 누적 가능성을 검토한 후 결정한다.
4. 실제 브라우저와 배포 서버 경로에서 최종 확인한다. 이후 별도로 응답 지연 분포, 동시 요청, 서버 장애·세션 만료를 검증한다.
