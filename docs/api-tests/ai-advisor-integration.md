# AI Advisor 내부망 API 연결

공통 AI Advisor는 브라우저와 같은 출처의 Next.js API를 통해 사내 채팅 서버에 연결한다. 답변과 표를 한 번에 받고, 서버가 돌려준 대화 ID를 다음 질문에 재사용한다.

## 화면에서 확인하기

일반 업무 화면은 왼쪽 아래 **AI Advisor**, 마스터 대시보드는 오른쪽 아래 **AI Advisor**를 연다. 두 진입점 모두 같은 대화 컴포넌트와 내부망 API를 사용한다.

1. **8월 24일 소요량 상위 3개**를 누르면 실제 조회한 자재 3건을 표로 볼 수 있다. 시작 질문의 날짜는 2026년이며 테스트에서 확인한 데이터 기간을 명시했다.
2. **같은 날짜의 계획 소요량 1위**로 후속 질문을 보낸다. 응답으로 받은 대화 ID를 재사용한다.
3. **8월 전체 계획 소요량**은 큰 표와 일부 결과 표시 안내를 확인하는 예시다. 표시 행 수를 전체 건수로 해석하지 않는다.

패널 상단에 서버의 데이터 기준일과 계획 조회 종료일을 표시한다. 기준일 조회에 실패해도 채팅은 사용할 수 있고 기준일만 다시 조회할 수 있다. 과거 날짜를 오늘의 실시간 상태로 표시하지 않는다.

답변을 기다리는 동안 전송과 시작 질문은 비활성화된다. **요청 취소**는 대기를 중단하고, **다시 시도**는 마지막 질문을 중복 말풍선 없이 재전송한다. **새 대화**는 진행 중 요청을 중단하고 새 세션을 시작한다. 패널을 닫았다 열면 같은 페이지에서 대화가 유지되며, 전체 새로고침이나 Advisor 컴포넌트가 분리된 화면 간 이동으로 언마운트되면 초기화된다. 서버의 장기 대화 보관 기능을 구현한 것은 아니다.

표 수치는 한국어 숫자 형식과 최대 소수 6자리로 표시하고, 품목코드·날짜·단위·앞자리 0은 보존한다. 답변 본문은 서버 문장을 표시하므로 단일 값 문장에 긴 소수점이 남는 등 원본 서버의 답변 품질 제약은 유지된다.

## 답변 대기 안내와 응답 시간

2026-09-09 같은 출처 채팅 라우트에서 정상 요청 3건을 순차 측정했다. 세 건 모두 HTTP 200이며, 세션 ID나 실제 자재 행은 측정 기록에 저장하지 않았다.

| 조회 조건 | 전체 응답 시간 | 표 크기 |
| --- | ---: | ---: |
| 8월 24일 소요량 상위 3개 | 13.609초 | 3행·4열 |
| 8월 25일 소요량 상위 2개 | 13.425초 | 2행·4열 |
| 8월 전체 계획 소요량, 자재별 | 15.240초 | 18행·4열 |

평균 14.091초, 중앙값 13.609초였다. 모두 본문이 JSON 한 청크로 도착했고 최초 본문 이후 완료까지 0.071~0.257ms였다. 따라서 **서버의 실제 중간 처리 단계는 알 수 없다.** 3건의 측정은 보장 시간이나 부하 시험 결과가 아니다.

대기 카드는 **질문 의도 파악 → 조회 조건 구성 → 데이터 조회 → 답변 정리**의 예상 흐름을 표시한다. 초기 측정값 기준 약 3·6·10초에 안내가 바뀌며, 시간이 지나 지난 예상 단계에는 초록색 체크를 표시한다. 체크는 화면의 예상 흐름이 다음 단계로 넘어갔다는 뜻이며, 실제 서버 작업의 완료 판정이나 완료율을 뜻하지 않는다. 카드에 예상 안내임을 명시하고, 답변이 먼저 도착하면 어떤 단계에서든 즉시 답변과 표로 전환한다. 안내를 끝까지 보여 주려고 응답을 지연시키지 않는다.

- 처음에는 최근 응답 기준 **약 13~16초**를 안내한다. 이후 현재 화면에서 성공한 최근 5회의 전체 응답 수신·검증 시간을 메모리에 저장해 예상 범위와 단계 간격을 보정한다. 오류·취소는 보정에서 제외하며 서버나 브라우저 저장소에 별도 기록하지 않는다.
- 경과 시간, 부드러운 활성 점 애니메이션, 지난 예상 단계의 초록색 체크를 제공한다. 단계는 클릭하지 않는 안내 목록이며, 설명 펼치기 문구와 클릭 동작은 없다. 동작 줄이기 환경에서는 반복 애니메이션을 끈다.
- 초기 기준 약 20.5초부터 지연 안내, 60초부터 오래 기다리는 경우의 안내를 표시한다. 실제 최근 응답이 길어지면 이 기준도 함께 조정한다. 마지막 예상 단계에서도 실제 응답을 계속 기다린다.
- **요청 취소** 후 **다시 시도**하면 경과 시간을 새로 시작한다. 패널을 닫았다 열면 요청 시작 시각을 유지해 경과 시간과 예상 단계가 이어진다. **새 대화**는 요청과 대화를 초기화하고 최근 시간 보정값은 유지한다.

구현: `AdvisorWaitingCard.tsx`, `utils/ai-advisor-progress.ts`, `use-ai-advisor.ts`. 같은 공통 컴포넌트를 사용하므로 일반 업무 화면과 마스터 대시보드에 함께 적용된다.

2026-09-09 최초 대기 UI 구현 당시에는 시간 측정 훅 12개 시나리오와 예상 단계·카드의 격리 검증 64개가 통과했다. 당시 실제 Chrome에서는 네 단계의 전환, 설명 펼치기, 답변 도착 시 카드 제거, 최근 응답 기준 보정, 취소 후 재시도 시 00:00 초기화, 패널 재열기 시 00:05에서 이어짐을 확인했다. 1920·1500·1200 CSS 픽셀에서 카드가 화면 안에 배치되고 body의 가로 넘침이 없었다. 실제 서버를 일부러 지연시키지 않았으므로 20초·60초 안내는 가상 시계로 검증했다. 타입 검사와 변경 파일 ESLint는 통과했고 전체 ESLint는 기존과 동일한 오류 89개·경고 63개였다.

같은 날 후속 요청으로 **‘눌러서 설명 보기’ 문구와 단계별 설명 펼치기 동작을 제거**하고 **지난 예상 단계에 초록색 체크를 표시**하도록 변경했다. 바로 위의 설명 펼치기 검증과 검사 건수는 후속 변경 이전 구현에 대한 기록이다. 현재 화면의 초록색 체크도 응답 시간에 따른 예상 표시이며 실제 서버 작업의 완료를 확인한 결과는 아니다.

후속 변경은 실제 Chrome 요청에서 설명 문구·단계 버튼이 없는 상태, 초기 체크 0개와 11초 시점의 초록 체크 3개·현재 단계 스피너, 응답 도착 후 실제 3행 표로 전환됨을 확인했다. 타입 검사와 변경 파일 ESLint는 통과했고 전체 ESLint의 기존 오류 89개·경고 63개는 동일했다.

## 서버 설정

기본 연결 주소는 `http://192.168.0.157:8793`이다. 주소를 변경할 때만 프로젝트 루트의 `.env.local` 또는 배포 서버 환경변수에 다음 값을 지정하고 Next.js 서버를 다시 시작한다.

```dotenv
ADVISOR_API_BASE_URL=http://192.168.0.157:8793
```

값에는 서버의 기본 주소를 지정한다. 경로는 연결 코드가 `/api/chat`, `/api/data-meta`로 결정한다. 서버 전용 설정이므로 `NEXT_PUBLIC_` 접두사를 사용하지 않는다. Next.js를 실행하는 PC 또는 배포 서버가 해당 사내 주소에 접근할 수 있어야 한다.

브라우저는 `/api/ai-advisor/chat`과 `/api/ai-advisor/meta`를 호출한다. 따라서 사내 API의 CORS 사전 요청 실패 문제 없이 같은 출처로 요청할 수 있다. 기존 Ollama `/api/chat` 연결은 별도로 유지한다.

## 화면용 계약

| 경로 | 요청 | 성공 응답 |
| --- | --- | --- |
| `POST /api/ai-advisor/chat` | `{ query: string, session_id?: string }` | `{ answer, session_id, table, status }` |
| `GET /api/ai-advisor/meta` | 없음 | `{ as_of_date, snapshot_date, forecast_end_date }` |

채팅 응답의 `session_id`와 `table`은 없을 때 `null`이다. `status`는 `success` 또는 `empty`이며, 표가 없다는 이유만으로 빈 결과로 판단하지 않는다. 정상 단일 값 답변도 `table: null`로 올 수 있다. 표의 열은 `columns: string[]`, 행은 `rows: string[][]`, 잘림 표시는 `truncated: boolean`, 추가 요약은 `summary: Record<string, string>`이다.

서버는 질문의 앞뒤 공백을 제거한 뒤 유니코드 문자 기준 1~2,000자를 검사한다. 대화 ID는 비어 있지 않은 최대 128자 문자열만 허용한다. 원본 API의 추가 필드인 `sql`, `sources`, `intent`, `model_used`는 화면 응답에 포함하지 않는다. 표의 모든 셀 타입과 행별 열 수, 실제 달력에 존재하는 날짜도 검증한다.

## 오류와 대기 처리

오류 응답은 `{ error: 한국어 안내, code, session_id?: string | null }`이며, 원본 SQL 오류나 서버 오류 본문은 전달하지 않는다.

| HTTP | 코드 예 | 의미 |
| --- | --- | --- |
| 400 / 415 / 422 | `INVALID_JSON`, `INVALID_CONTENT_TYPE`, `INVALID_INPUT` | 요청 형식 또는 입력 오류 |
| 422 | `QUERY_FAILED` | 관측된 조회 생성·검증 실패 답변 |
| 422 | `UPSTREAM_REJECTED` | 사내 API가 질문을 거절함 |
| 429 | `UPSTREAM_BUSY` | 사내 API 요청 제한 |
| 499 | `REQUEST_CANCELLED` | 클라이언트 요청 취소 |
| 502 | `UPSTREAM_UNAVAILABLE`, `UPSTREAM_HTTP_ERROR`, `INVALID_RESPONSE` | 연결·서버·응답 형식 오류 |
| 503 | `INVALID_CONFIGURATION` | 연결 주소 설정 오류 |
| 504 | `UPSTREAM_TIMEOUT` | 120초 대기 시간 초과 |

사내 API가 HTTP 200에 담아 보내는 알려진 조회 실패 문구는 HTTP 422로 변환한다. 이 구분과 빈 결과 판정은 현재 관측된 문구에 기반하며, 원본 API가 구조화된 상태 코드를 제공하기 전에는 새로운 실패 표현을 모두 판별할 수 없다. 오류 응답에 유효한 대화 ID가 있으면 후속 질문에 이어 쓸 수 있다.

요청과 응답은 캐시하지 않고, 자동 재시도하지 않는다. 응답 본문 수신까지 최대 120초를 기다리고 클라이언트 연결이 취소되면 사내 API 요청도 중단한다. 연결 중단이 원본 서버의 모델 실행이나 대화 기록까지 취소한다는 의미는 아니다. 배포 플랫폼의 요청 제한 시간도 120초 이상의 응답을 허용해야 한다.

## 검증

2026-09-09에 어댑터를 모의 서버 응답으로 검증했다. 입력 거절과 유니코드 길이 경계, 세션 전달, 추가 필드 제거, 정상 단일 값, 빈 표와 빈 결과 문구, 조회 실패 변환, 모든 행의 열 수와 셀 타입, HTTP 오류, 비 JSON/잘못된 JSON, 네트워크 실패, 가상 시계 기반 120초 제한, 클라이언트 취소, 날짜 검증 등 16개 검증 그룹이 통과했다. 검사 스크립트는 임시 경로에 두었고 실제 자재 행이나 세션 ID는 기록하지 않았다.

실제 API의 응답 시간·데이터 기준일·질문 표현에 따른 제약은 [기존 실측 보고서](./2026-09-09-ai-advisor-chat-api.md)를 참고한다.

통합 구현에서는 대화 훅의 비동기 검증 44개와 표 숫자·열 분류 검증 51개도 통과했다. 실제 Chrome 화면에서 표 조회·세션 후속 질문·잘림 안내·취소·중복 없는 재시도·닫기 후 대화 유지와 1920/1500/1200 CSS 픽셀 배치를 확인했다. 코드의 타입 검사와 변경 파일 ESLint는 통과했고 전체 ESLint는 기존 오류 89개·경고 63개로 실패했다.

조건에 맞는 데이터가 없는 실제 요청은 표 없이 빈 결과 안내를 표시했다. 브라우저에서 공백과 2,001자 입력의 전송이 차단됐고, 같은 출처 서버 라우트의 공백·잘못된 JSON·잘못된 Content-Type 요청은 각각 422·400·415 및 한국어 오류로 거절됐다. 새 대화에서 기존 말풍선이 제거되고, Esc로 닫을 때 포커스와 배경 스크롤 설정도 복원됐다.

최종 마스터 대시보드 확인 중 내부 서버가 일시적으로 `ECONNREFUSED` 상태가 되어 연결 오류 UI를 확인했다. 이후 상태 조회가 HTTP 200으로 복구됐고, 화면의 **다시 시도**로 같은 질문 1개에 답변 1개·자재 표 3행이 정상 표시됐다. 이 결과 화면을 열어 두었다. 서버 중단 원인은 확인되지 않았으며 클라이언트 수정 때문이라고 판단할 근거는 없다.

독립 리뷰에서는 이전 실측 응답 11건을 현재 변환 함수에 대조해 SQL 실패 2건의 구조화된 오류 변환, 빈 결과 1건, 나머지 답변과 세션·표 보존도 확인했다.
